# RallyMate 视频上传与评分颗粒度开发指南

## 1. 本轮交付目标

本轮代码只解决真实工程链路，不输出演示分数：

```text
上传视频
  -> FastAPI 创建持久化任务
  -> SQLite WAL 队列
  -> 常驻 GPU Worker
  -> YOLO player / ball / racket Detect
  -> ROI COCO-17 Pose
  -> 基础跨帧 track_id + 场地结果
  -> frames.jsonl / annotated.mp4 / summary.json
  -> 对照 298 项 GS/FS 指标生成 scoring-readiness.json
```

`scoring-readiness.json` 回答三件不同的事：

1. 视频中是否观测到了该指标需要的原始证据；
2. 当前模型输出颗粒度是否足够；
3. 当前是否已经具备输出最终技术分的资格。

这三项必须分开。检测到球或球拍，不等于已经能计算击球点、拍面角度或技术等级。

## 2. 一条命令启动本地推理服务

```powershell
Set-Location '<仓库根目录>'
.\scripts\run_local_inference.ps1
```

脚本会在同一进程中启动：

- 上传 API；
- 一个常驻 GPU Worker；
- CUDA 设备 0 上的 Detect 与 Pose 模型。

启动后访问：

- 最小上传控制台：`http://127.0.0.1:8000/`
- OpenAPI：`http://127.0.0.1:8000/docs`
- 静态模型能力：`http://127.0.0.1:8000/v1/model-capabilities`

## 3. 上传接口

`POST /v1/jobs`，请求类型为 `multipart/form-data`。

| 字段 | 必填 | 默认值 | 说明 |
|---|---|---:|---|
| `video` | 是 | — | MP4/MOV/M4V/AVI/MKV |
| `court_mode` | 否 | `auto` | `auto/manual/disabled` |
| `write_annotated_video` | 否 | `true` | 是否输出标注视频 |
| `max_players` | 否 | `2` | 1–4 |
| `start_ms` | 否 | `0` | 起始时间 |
| `end_ms` | 否 | 空 | 结束时间 |
| `max_frames` | 否 | 空 | 仅用于短链路调试；正式分析留空 |

PowerShell 示例：

```powershell
$response = Invoke-RestMethod `
  -Method Post `
  -Uri 'http://127.0.0.1:8000/v1/jobs' `
  -Form @{
    video = Get-Item '.\FULL-TEST\c235227fffcd3290b60572d0c3f9cc85.mp4'
    court_mode = 'auto'
    write_annotated_video = 'true'
  }

$jobId = $response.id
Invoke-RestMethod "http://127.0.0.1:8000/v1/jobs/$jobId"
```

任务状态包含 `progress.phase / progress.percent / progress.message`。完成后返回可下载产物地址。

## 4. 输出产物

每个任务目录包含：

| 产物 | 用途 |
|---|---|
| `frames.jsonl` | 每帧检测、Pose、track_id、场地和时间戳 |
| `summary.json` | 覆盖率、运行环境、质量门禁和颗粒度摘要 |
| `scoring-readiness.json` | 298 项逐条模型可行性报告 |
| `analysis-report.html` | 可直接阅读和筛选的完整分析报告 |
| `annotated.mp4` | 可选的推理标注视频 |
| `preview.jpg` | 首帧预览 |

`scoring-readiness.json` 的每项结果包含：

- 指标编号、事件和阶段；
- 必需/可选依赖；
- 所需 J 关节；
- 当前依赖覆盖率；
- `observed_evidence_status`；
- `model_granularity`；
- `score_ready`；
- 明确阻断原因。

## 5. 当前模型对 298 项指标的真实结论

### Pose

- 298 项中 291 项依赖人体 Pose；
- 指标卡显式要求的 J 关节均能从当前 COCO-17 映射；
- 因此近期不需要立刻推倒 Pose 拓扑；
- 应先在网球动作数据上微调，并解决主球员轨迹断裂、遮挡和低置信关节；
- Pose-only 指标可以作为第一批事件/特征模块的开发对象，但没有事件切分前仍不能给最终分。

### 球

当前是通用 `sports ball` 检测框和简单 `track_id`。它不能可靠提供：

- 活动比赛球筛选；
- 击球前后连续轨迹；
- 精确触拍时刻；
- 球速、旋转和三维落点。

需要网球小球专项检测模型和时序轨迹模型。

### 球拍

当前只有通用球拍框，不能提供拍头、拍柄、拍面、甜区和拍面角度。所有依赖 `RK 专项关键点` 的指标都必须保持结构性阻断。建议独立训练球拍关键点模型，不把球拍关键点塞进人体 Pose。

### 场地与跟踪

- 固定机位应采用版本化四点米制标定；自动区域提示不能代替尺度标定；
- 当前简单 tracker 只能证明接口成立，不能作为生产级主球员、球和球拍连续轨迹。

### 事件与评分

当前没有 GS/FS 事件切分和经过真值标定的指标计算函数，所以 298 项最终分全部保持阻断。这是刻意的质量门禁，不是程序失败。

## 6. 下一阶段代码顺序

1. 先实现 pose-only 的 GS/FS 事件切分；
2. 建立人工真值测试集，测 Pose PCK、事件 F1 和边界误差；
3. 训练 ball/racket 专项模型；
4. 固定机位标定版本化；
5. 为每项指标实现特征函数和真值阈值；
6. 只有通过独立测试集后，才把 `score_ready` 从 `false` 改为 `true`。
