# 教练视频标注操作指南

适用日期：2026-10-04。适用于本轮新收集的网球视频试标；首先收集人工观察，再决定哪些字段进入模型训练、评估或技术等级标定。

**现在就可以开始：给教练原视频、[空白 Excel 模板](../examples/coach-annotation-pilot/教练试标模板_2026-10-04.xlsx) 和本指南。** 教练主要使用播放器和 Excel，工程人员负责整理 JSON。目前只有一位教练也可以先统一口径和初筛；第二位教练加入后再独立标注并复核分歧。无需等待生产评分标定，也无需使用历史 FS09 包。仓库目前没有可直接上传任意视频、完整标注正手／反手／发球的通用网页。

## 1. 首批怎么选，给教练什么

建议先试标 **30–50 个动作**，用于发现定义不清、字段难填和教练分歧。这个数量是工作启动建议，**不是统计充分性、模型准确率或正式测试集规模的依据**。

1. 先选 3–5 个独立的讲解样例，与教练讨论下文的动作和阶段定义；这些样例标为“口径讨论”，不计入后续独立一致性评估。第二位教练后来加入时，先用这些样例熟悉相同口径，不看第一位的试标答案。
2. 试标尽量包含正手、反手、发球；加入少量看不清、动作不完整或并非挥拍的片段。某一类没有素材就如实记缺口，不凑标签。
3. 尽可能覆盖不同球员、拍摄场次、正面／背面／侧面视角，并保留部分遮挡、出画、镜头移动的情况。首轮不用追求所有组合齐全。
4. 除了方便复看的动作片段，保留对应原视频和动作前后的上下文。不要只按系统检测出的候选截取；至少有连续原视频供教练自行找动作，才能发现系统漏检。

组织者给每位教练一份相同的材料：

- 原视频文件，以中性编号命名，例如 `V001`；不把“正手”“高分”“动作错误”等答案写进文件名。
- 一份独立的 [教练试标模板_2026-10-04.xlsx](../examples/coach-annotation-pilot/教练试标模板_2026-10-04.xlsx)，包含“动作片段”“阶段时间”“技术观察”三页，分别有 50／300／300 行空白及下拉选项；教练 A 和 B 各存自己的副本。模板没有预设真实标签，等级列留空，统一等级描述后再填。
- 球员定位说明，例如“近端蓝衣球员”。只说明观察谁，不展示自动跟踪、动作分类或骨架结果。
- 本指南和统一的阶段口径。工程编号、文件校验值、来源帧号由组织者补齐，教练不用手填技术字段。

**盲标时不发系统参考分、报告、自动骨架、预测动作、候选中心、推荐阶段边界或另一位教练的答案。** 参考分可能反映视频证据条件，不能作为动作技术好坏的答案。系统结果可在独立提交封存后用于误差分析。

本次只使用用户已授权的新素材。旧包的技术 QA 状态不会阻止这批素材的人工收集；旧包也不应被改成新任务来覆盖历史记录。

## 2. 教练实际怎么操作

### 第一步：先正常速度看一遍

用能够播放原视频、暂停和定位时间的播放器打开文件。先确认目标球员，再正常速度观看指定范围。需要时暂停、慢放和回看；本指南不假定某个播放器的逐帧快捷键。

填写“动作片段”页：视频编号、观察的球员、教练编号、片段编号（用于关联同一次动作）、动作类别、开始／结束时间、看不清的原因。动作是否完整、是否被裁剪写在备注中，表格没有独立的“是否完整”列。片段编号由每位教练独立编号即可，之后由组织者匹配，不要求先接受机器给出的动作列表。

若只看了指定片段，就记“已审阅该片段”；只有真的看完整部原视频，才能记“全片审阅完成”。未标出事件可能代表“尚未审阅”，不能直接当作“没有动作”。

### 第二步：所有时间都按原视频秒数填

表内统一使用原视频从开头起算的秒数，例如 `12.350`，不填 `00:12:350`，也不把第 12 帧写成 12 秒。表格显示三位小数只是格式，**不意味着观察精度达到 1 毫秒**。

- 播放完整原视频：直接记录原视频时间。
- 播放从原视频裁出的片段：组织者先提供经过核对的起点偏移。例如片段起点为原视频 `10.000` 秒，片段中的 `2.350` 秒对应原视频 `12.350` 秒。
- 经变速、抽帧或拼接的视频不能只加一个偏移；优先回到原文件，由工程人员校准时间对应关系后再使用。
- 精确时点无法判断时，时间留空，填“不能确定”及原因；能圈定一个范围时记录最早／最晚可能时间或估计误差。不要用 `0` 代替未知。
- 镜头切换、目标球员换人或视频剪切应拆成不同片段；不能跨断点连成一个完整动作。

工程交接时将秒数转换为整数毫秒，例如 `12.350 → 12350`，保留原填值及误差。如果需要逐帧标签，使用源视频真实时间戳／帧对应，不按猜测的帧率反推。

### 第三步：标动作类别，不急着评好坏

“动作类型”下拉实际为 `正手／单手反手／双手反手／发球／截击／高压球／切削／其他／无法判断`，按看得清的类型选择；无法区分时选“无法判断”，在备注说明可能的动作及原因，不强选单手或双手反手。持拍手为左／右、是否接发球，可在看得清时另记；不能确认的内容留空并写原因。

“反手”以球员和持拍动作判断，不按画面左边／右边判断。“接发球”需要发球上下文，单凭一次挥拍不能确认。“不能确定动作类别”不妨碍记录看得清的肩、髋、手腕或脚步变化。

动作开始取本次击球相关准备首次清楚出现的时刻；结束取本次随挥及可见恢复完成、或转入下一动作的时刻。连续对拉时尽量区分相邻动作，重叠或边界模糊就注明。开头或结尾被截断的动作记“不完整”，不要补想象中的阶段。

### 第四步：回看并填“阶段时间”

下面是**本次试标建议口径**，由教练在讲解样例中先统一。每个阶段填写可观察的开始和结束；关键瞬间单独填写时点。若定义需要修订，记录口径版本，已标素材要决定是否重标，不能悄悄混用。

**先按现有表格填：**“阶段”下拉实际为“准备、加速挥拍、随挥、脚步启动、制动、恢复、确认触球”。同一动作可以填写多行，用片段编号关联。下表中的引拍、抛球、蓄势等细分写在备注中，例如两行都选“准备”，分别备注“抛球”和“蓄势”；它们不是额外的下拉选项。向前挥拍可选“加速挥拍”并备注“可见向前挥拍区间”，发球备注“可见向上挥拍区间”，但这个人工条目只表示可观察的挥拍过程，不能证明实际速度一直增加。工程交接须保留备注和人工原意，再决定对应关系。

| 动作 | 建议阶段 | 如何在视频中判断 |
|---|---|---|
| 正手／反手 | 准备 | 进入本次击球准备，到清楚的引拍开始；已在准备姿势中的片段可无法确定开始 |
| 正手／反手 | 引拍 | 球拍／持拍臂为本次击球向后组织，到转入向前挥拍；不强行要求每个动作都有独立清楚边界 |
| 正手／反手 | 向前挥拍 | 持拍臂／球拍向预期击球区前移；与随挥的分界若因球拍或球不可见而不能确定，明确留空 |
| 正手／反手 | 随挥 | 可辨认的击球后延续动作；不能确认击球时点时，允许只圈可见随挥区间并写边界不确定 |
| 正手／反手 | 恢复 | 随挥后重新组织身体、准备下一动作；可与脚步回位重叠 |
| 发球 | 准备／抛球 | 发球准备及可见抛球过程；抛球释放时点只在看清时单独记录 |
| 发球 | 蓄势／引拍 | 本次发球向上挥拍前可见的身体和持拍臂组织；不以想象的受力峰值作为边界 |
| 发球 | 向上挥拍 | 持拍臂／球拍向击球区域的明显上挥过程 |
| 发球 | 随挥／恢复 | 发球后的可见延续、落地与恢复；落地作为独立脚步观察，不能直接解释为发力大小 |

**触球是独立关键时点。** 只有直接看清球拍与球接触或有独立证据时，才在阶段页选“确认触球”并填写可观察状态、时间和误差；在开始和结束秒数列填写同一时刻，表示单一时点。球太小、模糊或遮挡时，触球时间留空，可观察状态选择相应的无法判断项并写原因；行中的“确认触球”只是待检查项目，不能绕过不可观察状态解释为触球已确认。不能把手腕速度峰值、模型候选中心、画面上看似接近的时刻填写成“确认触球”。

阶段看不清时应区分：尚未标、被遮挡／模糊而无法判断、被片段截断、不适用。动作本身也可能不确定。不要把这些都填成“没有该阶段”。

当前规则后端使用 `preparation / acceleration / follow_through` 三段的推断契约，并非上述完整人工阶段真值。人工“向前挥拍”也不自动等于运动学“加速”。工程人员应保存原标签，再定义映射和测试，不能仅按名称直接覆盖。

### 第五步：分别记脚步、可见性和技术观察

脚步不必与挥拍分成互斥片段，可与同一次挥拍关联并有重叠时间窗。首轮可用通俗名称记录：垫步／分腿垫步、启动第一步、横移或交叉步、制动、回位、其他、不能确定。

- 能看清哪只脚离地、落地、开始移动，就记对应时点、左右脚和误差；左右指球员身体左右，不是画面左右。
- “脚开始移动”“脚接触地面”和“身体速度降低”分别记录。姿态画面不能直接证明地面反作用力、重心受力或制动力峰值。
- 肩、髋、手肘、手腕、膝、踝及脚趾／脚跟分别记录可见性；优先补充影响当前判断的部位及时间窗。一个手腕遮挡不等于髋和双脚也不可用。
- 常用原因：被身体或物体遮挡、超出画面、太小、运动模糊、无法区分左右、镜头运动、主体身份不清。
- 机位可记正面、背面、左／右侧、斜向、不能确定；画面里可观察到的二维变化可以照常描述，但不能直接写成准确的三维转体角度。

“技术观察”页每条写清 **具体观察 + 对应时间窗／阶段 + 能否判断 + 理由**。例如“本次随挥前半段手腕被躯干挡住，无法判断手臂路径”，比“挥拍不好”更可复核。若教练提出技术问题或练习建议，也要把看到的现象与教练解释分开保存。

本轮不强制打综合分。后续如需 A–E 等级或排序，先约定指标、等级描述及样例，并让教练在看不到系统数值时独立评价；无法判断不是 E，也不是 0 分。表格“阶段时间”页的起止值是原视频秒数，误差列按表头填写毫秒；“技术观察”页需同时保留事实、判断、证据时间、规则版本和不可评价原因。

## 3. 两位教练怎样独立标，怎样处理分歧

只有一位教练时可以先完成素材初筛和第一份标注，但此时不能报告双人一致性，也不能声称已完成独立复核。以下流程在第二位教练加入后实施。

1. 组织者固定素材和口径版本，给 A、B 各一份空表。双方独立观看和填写，不交换答案；原始文件按“批次－角色－版本”保存。
2. 收齐后封存各自的原始提交。工程人员先检查视频和时间对应、必填信息、负时间、起点晚于终点等格式问题；格式检查不能代替教练判断。
3. 组织者按同一球员、同一原视频、相近时间段匹配事件，单独列出 A 有 B 无、B 有 A 无、动作类别不同、阶段边界不同、可见性不同的情况。不要先把双方平均成一份答案。
4. 由第三位教练 C，或双方在独立提交封存后共同复核分歧。仍然看不到系统分数。保留 A、B 原答案、裁决、理由和裁决者；若无法解决，就保留“有分歧／不能确定”。
5. 首轮总结哪些字段经常分歧、哪些视角无法标，再调整下一轮素材和定义。一致率只能按真实已完成、可匹配的记录计算，须同时报告漏标和不可判断数量。

关键边界的容差应在看片前根据视频时间分辨率和标注目标统一。可以先把超过双方记录误差范围的边界差异交复核；不能为了提高一致率而事后扩大容差。教练之间一致也不自动证明标签正确。

## 4. 素材分组和防止训练／测试泄漏

组织者维护 `player_id`、`session_id`、`source_video_id` 和 `split_group_id`，使用匿名编号。相同原视频的裁剪、重编码、重复上传、相邻或重叠片段必须归同组；同一拍摄场次的多机位也要关联。

在训练、调阈值和正式测试划分前，先按球员和场次分组。同一球员或同一场次不应随机拆成大量片段后分别进入训练和测试。若目标是验证对新球员的表现，应把测试球员整体留出；若目标仅是同一球员的新场次，应明确这个较窄的评估范围。

本轮口径讨论及调试用的试标素材属于开发用途。后续另留正式测试组，在模型、阈值和映射确定前封存；看过测试答案并据此修改规则后，该组就不再是未见测试集。30–50 个动作试标本身不支撑“已经训练出网球分类器”或准确率承诺。

## 5. 现有网页哪些能用，哪些不能直接用于本轮

以下说明基于本地代码和包的核验，没有假定外部网页工具的操作。**本轮新视频优先用前面的原视频＋表格流程；这里是可选的专项工具。**

### 可用：M96 关节点审计页，固定素材

入口文件为 [A 角色页面](../data/annotations/m96-halpe26-development-pilot-v1/annotator-A/review.html) 和 [B 角色页面](../data/annotations/m96-halpe26-development-pilot-v1/annotator-B/review.html)。使用专用本地服务打开，不能把任意新视频替换进冻结包。

本次已对现有 A、B 包执行只读 `--validate-only`，均返回 `valid`。这是文件／来源校验结果，**不是有人已完成标注，也不是浏览器全流程验收**。服务目前不因本指南而自动启动。

由组织者在项目根目录的 PowerShell 中启动 A：

```powershell
& .\runtime\rtmpose\.venv\Scripts\python.exe .\scripts\serve_m96_pose_pilot.py --bundle .\data\annotations\m96-halpe26-development-pilot-v1 --role A --port 8765
```

打开命令输出的 `url`。在本目录结构和上述端口下为：`http://127.0.0.1:8765/data/annotations/m96-halpe26-development-pilot-v1/annotator-A/review.html`。B 使用另一终端和隔离的浏览器用户配置／电脑：

```powershell
& .\runtime\rtmpose\.venv\Scripts\python.exe .\scripts\serve_m96_pose_pilot.py --bundle .\data\annotations\m96-halpe26-development-pilot-v1 --role B --port 8766
```

只读校验可在对应命令末尾加 `--validate-only`；不启动网页。端口被占用时选另一个可用端口。服务只监听本机 `127.0.0.1`，停止用 `Ctrl+C`。

教练在该页填写 `annotator ID`，选择“任务”，点击画面记录当前关节点，用“上一点／下一点”切换；点不可见时选“不可见原因”并点“标为不可见”，不要猜坐标。结束时用“导出 CSV”保存；中途草稿也可导出，再用“导入本角色 CSV 恢复草稿”继续。浏览器草稿不能代替提交备份。

此包有 3 部固定开发视频、24 个抽取帧、每位教练 624 个 Halpe26 关节点任务；完整提交必须覆盖本角色全部任务。该包目标球员选择按协议执行：画面中视觉尺寸最大的球员，尺寸并列时选水平中心更靠左者。它与新试标中组织者指定的目标球员是不同任务定义。

这项任务是**点位置和可见性审计**，不能代替正反手动作分类或阶段标注。它的协议明确是开发子集评估用途、不是训练数据发布或技术等级标定。A、B 完成后可由工程人员使用 [M96 提交校验脚本](../scripts/validate_m96_pose_pilot_submission.py) 和 [分歧裁决包构建脚本](../scripts/build_m96_pose_pilot_adjudication.py) 处理；原包保持不变。

## 6. 工程交接：三类标签不要混成一类

| 人工记录 | 已有接口／工具 | 当前适用边界 |
|---|---|---|
| 动作事件真值：发生了什么、在哪段时间、阶段是否可见 | [events.schema.json](../contracts/events.schema.json)、[M93 submission schema](../contracts/scoring-truth-event-annotation-submission.schema.json) | 既有事件枚举为 FS01／FS02／FS09；新正手、反手、发球及通俗阶段需新增明确映射或契约，不能改个字段名就导入 |
| 关节审计：指定原帧中关节点的位置和可见性 | [keypoint-ground-truth.schema.json](../contracts/keypoint-ground-truth.schema.json)、[M96 protocol](../data/annotations/m96-halpe26-development-pilot-v1/protocol.json) | 必须绑定原视频、源帧和主体；坐标为原完整画面 x／宽、y／高，左上为原点；不是裁剪图、躯干归一化或相机补偿坐标 |
| 脚步语义：支撑侧、目标方向、接触或稳定区间等 | [semantic-ground-truth.schema.json](../contracts/semantic-ground-truth.schema.json) | 仅限契约已有语义键；不可见时数值为 null 并给原因，不从机器估计补成真值 |
| 技术等级或排序：针对某个指标的教练评价 | [coach-label.schema.json](../contracts/coach-label.schema.json) | 兼容 A–E `grade` 或组内 `ranking`，需关联 video／event／indicator／annotator；没有现成的“综合 100 分”字段，也不表示标定已完成 |

M93 的阶段关键字为：FS01 的 `preload_ms / takeoff_proxy_ms / landing_proxy_ms / redistribution_ms / initiation_ms`；FS02 的 `direction_conversion_ms / support_extension_proxy_ms / lead_foot_motion_onset_proxy_ms / first_step_slowdown_proxy_ms`；FS09 的 `peak_speed_ms / deceleration_peak_ms / restabilization_onset_ms / stable_control_onset_ms`。名称中 `proxy` 是可观察代理，不是直接受力真值；不能让教练为了填满字段而猜测峰值。

既有 M93 可观察阶段写 `status=observed`、整数 `timestamp_ms`、空 `reason`；不可观察写 `status=unobservable`、`timestamp_ms=null` 和非空原因。新试标表还收集区间、截断、误差、动作类别等更丰富的信息，转换时要逐项核对，不能丢弃后假装完全兼容。

关节点不可见时坐标必须留空／null，不能填 `(0,0)` 或照抄模型点。左右关节按球员身体定义，Halpe26 的 26 点必须按协议顺序映射；其中心类点另依协议定义，不能靠教练自由命名。现有 keypoint 真值中的 `primary_player_id=1` 是约定的主角编号，需要工程映射，不能直接复制任意检测器 track ID。

旧 [truth pack 编译脚本](../scripts/compile_scoring_truth_pack.py) 与 [导入脚本](../scripts/ingest_scoring_truth_exports.py) 使用既定的事件、关节、语义、教练标签及全片审阅文件；只把符合接收条件的人工记录编译进真值。**本轮 Excel 和下面的新 JSON 不是这些工具的直接输入。** 新动作类别、细化阶段、可见性区间、主观解释和误差等没有现成映射的字段，应原样保留在新批次，待转换器及验证规则实现后再导入。不能向旧 `compiled` 目录写入试标草稿。

## 7. 本轮交付清单和 JSON 示例

每个批次交付：素材清单及原文件对应、口径版本、A 原始副本、B 原始副本、审阅完成范围、分歧清单及最终裁决副本。工程人员保留原件，生成新版本的结构化结果；仅当确实裁决完成，才标记为最终真值。未经审阅的空字段、未解决分歧和被截断的时间都保留状态。

本仓库新增两个工程交接示例：

- [annotation-template.json](../examples/coach-annotation-pilot/annotation-template.json)：空白模板，`events` 为空；`event_record_template` 只是字段说明，不是一条已完成标签。
- [fictional-example.json](../examples/coach-annotation-pilot/fictional-example.json)：**完全虚构的填写演示**，没有对应真实视频，禁止用于训练、评估、准确率计算或技术标定。

教练不用直接编辑这些 JSON。组织者先收 Excel；工程人员再按原视频毫秒时轴录入 JSON，并复核片段偏移。JSON 中可保留人工阶段与每阶段证据窗、触球是否可见、每个部位缺测原因、主体连续性／镜头断点、持拍手与机位的不确定性、教练及裁决版本、球员／场次分组等。未来接入可替换时序后端时，用这些字段检验模型是否在真实连续窗口内识别动作与阶段；不会因填了一份模板就生成训练好的网球分类器或自动技术分。

可直接发给教练的简短说明：

> 请只根据原视频独立填写，不参考系统报告，也先不要和另一位教练讨论。先标发生了什么动作和原视频中的起止秒数，再补能看清的阶段、脚步和技术观察。看不清可以留空，但请写原因及能确定的时间范围；尤其不要猜触球。每人保留独立副本，交回后再共同处理分歧。
