## 2026-11-09：单卡 4× 目标与本轮验证

本轮目标是同一 RTX 5070 Ti、同一完整源片 `FULL-TEST/0d6ab5053c602f81bb863071fce4a797.mp4` 的完整分析时间不超过 **347.599 秒**。历史已验收任务 `04792ff1-8ab3-4ad5-ad19-43217682e4f6` 为 13,116 帧、1390.395 秒；4× 是待实测目标，不能将配置值或局部实验倍率当成已实现。上传、首个报告和三维视频交付另计。

本轮开始时的持久配置已经包含 batch8、BF16 主干、CUDA Graph、准备与推理重叠、8 帧归档队列及 2 个三维场景准备线程。这些是基线已有能力，不作为本轮新增收益。下文早期日期描述的单帧默认和未启用状态只对应当时记录。

本轮生产代码的 CPU 修改保留原有数据内容：

- `rallymate_vision/quality.py`：合并画面统计的重复扫描；警告阈值、三位小数舍入边缘及非 uint8 输入保留原计算。原片 13,116 帧的数值和警告逐帧一致，另有阈值和舍入边界测试。
- `rallymate_scoring/source_assessment.py`：每个动作的原始窗口只深复制一次，供两个只读步骤复用；时间线仍独立复制。相同解释器和依赖下，402 个动作的完整 contextual 结果精确相同。

历史报告不能直接作为这次 CPU 优化的等价基线：本轮开始前，当前工作区的部分规则已由历史 0.75 改为 0.70，并增加动作阶段字段。因此历史产物对照明确记为 `comparison_abandoned_incompatible_historical_rules`；没有排除这些字段来伪造相等。带 cProfile 的 00–07 阶段已完成，仅用于定位热点，含大量 profiler 开销，不能当成优化前后速度。

完整 13,116 帧的组合实验进一步发现历史主体规则也不同：A 恢复上述五个 CPU 模块的修改前版本、检测图关闭，仍只得到 4,167 个有三维姿态的源帧，历史为 8,699；两者全部人物、球、球拍检测数量相同。首个姿态覆盖分歧在源帧 520，检测和相机记录逐字段相同，历史以 `unique_upper_lower_clothing_match` 认回人物，当前为 `target_identity_unmatched`，继而 `primary_not_visible` / `no_detected_subject`。当前 `subject_lock.py` 已有本轮开始前的 `foreground-clothing-reentry-v2`，改用排除背景颜色后的衣物证据；本轮没有修改或回滚该规则。原生成功人物记录由 15,328 变为 6,439，不能把较少的三维计算量当成提速，也不能仅凭覆盖数量判断哪一版人物关联正确。

因此该组合实验的 A=723.088 秒明确不作为历史 4× 目标的成绩，B 已经由现有取消机制停止；两棵归属进程树均确认退出、GPU owner 已释放、没有隔离遗留，全部产物保留。状态为 `non_equivalent_historical_pose_coverage`，证据见 `combined-full13116-ab-01/coverage-rejection-and-cleanup.json`、`historical-versus-A-coverage-summary.json` 和 `first-subject-coverage-divergence.json`。这项失败不推翻前述使用同一份完整历史原始输出、同一当前评分规则的 CPU ABBA，但目前仍没有通过验收的整片 4× 成绩。后续整片性能对照必须先固定相同的主体关联和评分规则，并核对实际处理的人物与完整三维覆盖。

首 521 帧另做了不调用 GPU 的主体关联回放：旧模块与历史任务、新模块与 A 的 `subject_identity` 均 521/521 帧逐字段相同；检测和相机输入也完全相同。第 518–520 帧前景特征和参考模板均有效，但新前景距离为 0.365939/0.336153/0.331155，超过 0.30；旧衣物距离为 0.299761/0.294419/0.285143。首次裁决原因分歧在第 515 帧，首次有无姿态分歧在第 520 帧。此项确认该段差异来自匹配距离门槛，而不是模板缺失或模型预热；没有改阈值，也不据此裁定哪版身份匹配更准确。证据为 `subject-lock-first521-replay-02/receipt.json`，覆盖范围仅源帧 0–520。

随后补做了**当前同一 v2 人物规则下，仅五个 CPU 模块不同、检测图均关闭**的完整单次对照，复用前述正常完成的 A，只新运行一次 B。计时统一使用 `trial.pipeline_wall_seconds`：**723.992 → 679.045 秒，减少 44.947 秒、6.208%，约 1.06619×**。源片 13,116 帧的 PTS、检测、人物关联、相机与主要人物时间线完全相同；15,704 条原生记录的状态和绑定完全相同，6,439 个成功主体的全部关键点、完整网格、相机、焦距和面拓扑均参与比较，无跳过。198 个事件核心字段、858 条评分决策相同，用户报告均有 29 个动作段、总分 88.55，五维为 93.43/70.2/81.2/99.51/98.41。

该整片对照**没有全部数值逐值相同**：二维关键点最大差 0.0001831 像素，三维点约 4.649e-6、网格顶点约 4.783e-6、相机约 5.341e-5；焦距与面拓扑精确相同。完整评分字段中有连续值和 75 处证据帧列表长度变化，全部差异保留，未按容差自动通过。A/B 没有重复 A，B 还增加了采样监督，因而此项是单轮诊断，不是严格 ABBA 的稳定提速成绩；不能用历史 1390.395 秒除以本次 679.045 秒，两者主体规则和工作量不同。模型加载/预热、独立用户报告构建、上传和后台三维视频制作不在该 pipeline 计时内，用户报告构建耗时单独保留。

### 2026-11-02 GPU 数据流水线第一阶段

新增 `RALLYMATE_SAM3D_BATCH_PREPROCESS=1` 实验开关，默认关闭。`sam3d_batch_preprocess.py` 保持官方 OpenCV 裁剪、相机与仿射元数据，将最多 8 个人物的 uint8 裁剪图合成一次 H2D 上传，在 GPU 转 float32 并归一化。对全部 256 种 uint8 值验证归一化；若 GPU 除法不能逐位匹配官方 CPU 值，使用官方值查表。

host pinned 和 device uint8 缓冲固定复用，各自容量最多 24 MiB；最终 float 模型输入独立分配，不能将 staging 上限理解为总显存上限。CUDA 事件覆盖首次分配的流依赖、前次 H2D 完成后才能重填 host、前次读取完成后才能覆盖 device，以及当前 H2D 完成后才启动计算。关闭 executor 时等待本实例事件后释放缓冲。

已有单帧 GPU transform 本来就会逐人物上传 uint8 crop；本次改善点是将 N 次上传合为 1 次，并复用 staging，不能描述为从全 CPU 预处理直接迁移到 GPU。仿射裁剪和 RGB 转换仍在 CPU，runner 前后同步及输出回传仍存在，也没有实现跨批模型前向重叠。

benchmark 新增 `--batch-preprocess 0/1`，显式参数优先于环境；回执强制验证确实单次上传、真正单次批前向。所有 70 点、完整 mesh、相机、焦距、拓扑与来源绑定均参与比较。61 项 CPU 测试在 Windows 与 WSL Ubuntu 通过；实际 GPU 收益与端到端结果以 `reports/upload-gpu-mainline-20261102/` 的后续报告为准，测试通过本身不代表提速或生产已启用。

WSL 下额外执行了真实 CUDA 小张量校验：16×16 crop，人数依次 8/3/8/1，全部 256 种 uint8 值逐位匹配官方值，host/device 地址复用且此前 float 输出没有被覆盖，事件等待和关闭正常。本机实际采用 GPU 查表归一化。证据为 `linux-cuda-staging-smoke.json`；此项未加载 SAM，也没有测量性能。

**Windows 真实 SAM 对照：**320×568 单人视频的同一 16 帧（33–48），graph8、blocking-sync、每个独立 worker 三轮单帧/批次交替，worker 顺序为预处理 off/on/on/off。单帧中位数约 12.0–12.2 FPS，batch8 约 18.4 FPS。新 staging 的两轮 worker 中位数为 18.370/18.482 FPS，旧 batch 路径为 18.384/18.446 FPS；合计差异约 +0.06%，不足以证明额外提速，因此继续默认关闭该开关。真 batch 本身的吞吐改善与新 staging 的收益必须分开报告。

## 当前状态

已经实现真正的多帧 BODY 批推理，并在本机 RTX 5070 Ti 上执行真实模型验证。不是把逐帧调用放进多个线程：同组人物 crop 组成 `B=N, P=1`，调用一次官方 `model.run_inference`，再按原始帧和人物拆回结果。

生产默认仍为单帧。本次开发与基准使用隔离进程，尚未把正在运行的 Cloudflare 入口服务改成批推理。小样本数值一致性不等于完整视频事件和评分验收，更不能代替朋友的 500 MB 视频公网测试。

## 数据流与边界

1. 按原始 PTS 解码，保存每帧时间戳、帧号及像素引用。
2. 检测可使用已有独立批次开关；tracker、相机运动、主体锁定和初始主体缓冲仍按时间顺序执行。
3. 身份确定后，组装最多 8 帧的 SAM 请求。每帧保留自己的原图、bbox、相机参考 epoch、人物 track ID 和 selection epoch。
4. IPC 使用独立共享内存槽传递每帧原图；非共享内存模式仍支持临时 NPY。请求编号必须匹配，一次只允许一个在途请求。
5. worker 将有效人物展平，按人物上限分组，每组最多 8 人。保留官方逐图 crop、相机内参与仿射变换，合并张量后一次前向；仅剩一人时使用现有单人路径。
6. 输出全部原生 70 关键点和完整人体网格，按请求顺序恢复帧槽，依次归档、写 JSONL、评分。空人物、无效框和失败槽均有明确状态。

没有修改模型权重、分辨率、浮点精度、关键点定义、抽帧策略或评分公式。当前仅支持官方默认 FOV 的 BODY 模式；full/hand、多线程共享同一个模型和跨任务动态组批不属于本次实现。

关键代码：

- `src/rallymate_vision/sam3d_batch.py`：校验固定版本源码；组装官方批输入并执行一次前向。
- `src/rallymate_vision/sam3d_runner.py`：批 IPC、人物微批次、原生输出校验与 worker 生命周期。
- `src/rallymate_vision/sam3d_adapter.py`：逐帧身份准备和有序输出解包。
- `src/rallymate_vision/sam3d_pipeline_batch.py`、`pipeline.py`：有限缓冲、顺序发布、取消与归档。
- `src/rallymate_vision/sam3d_cuda_graph.py`、`sam3d_forward_graph.py`：批尺寸对应的独立 CUDA Graph。

## 为什么仅把 N 调大不够

原有 CUDA Graph 为单人物形状捕获。直接使用两帧 batch 会退出单人图优化，在最初测试中比原先单帧还慢。新增实现保留原单帧图，另外按指定人物数捕获 body head、backbone 和 decoder layer 的固定形状图。

每种形状都有独立输入/输出缓冲、状态与回执。batch=1 在批推理前后仍可使用原图；不同形状不会错误地重放单人图。官方 decoder 的 `context_pe` 允许前导维为 1 并广播，只有这一已验证参数允许此例外。

最多额外缓存两种形状。body head 和 forward 模块各有 512 MiB 的额外图保留预算；后者由 backbone 与各 decoder layer 共享。可用显存不足或保留预算超限的图保持 eager 执行，并记录原因。预算限制的是观测到的保留分配/预留增量，不是整个进程显存或捕获瞬间峰值的硬上限。

实测同时配置 `2,4` 时，形状 2 可先占满 forward 的预算，导致形状 4 无法捕获。因此固定单人视频优先只缓存实际要用的形状。图捕获有冷启动成本，短视频未必受益。

## 内存、失败和计时

- pipeline 的 SAM 待处理原图预算为 64 MiB；超大单帧独立处理。解码预取、检测、主体初始化各有独立缓冲，不能把这个数字当成进程总内存上限。
- IPC 每批最多 8 帧、原图总量最多 128 MiB。共享内存池同时限制保留容量，跨任务遇到不同尺寸时不会无限累积；子进程在回执前释放这一批映射。
- worker 每帧最多接收 4 个人物框，实际前向按 `BATCH_PERSONS` 再分组。8 帧、每帧 2 人、人物上限 8，需要两次前向。
- 输出在发布前校验数量、70 点维度、有限值、相机与焦距；失败保留所有输出槽。不会对失败批次自动逐帧重跑，避免掩盖 OOM 或产生重复结果。
- 正常取消或批次部分捕获失败时，回收尚未发布且校验归属与 SHA256 的本次 mesh 文件；保留共享拓扑、已归档文件和已交给异步归档器的槽。不会扫描或删除历史缓存。
- 超时、错误回执或取消终止 worker 时，先停止其进程树，再释放共享内存，避免旧 worker 读取被覆盖的帧。
- 每条原生记录的 `inference_ms` 是该人物分摊的批次墙钟耗时；`batch_execution.wall_ms` 与 IPC 计时属于整批，不能跨记录相加。pipeline 的姿态计时按实际调用累计。

## 配置

| 环境变量 | 默认 | 含义 |
| --- | --- | --- |
| `RALLYMATE_SAM3D_BATCH_FRAMES` | `1` | pipeline 每批源帧数，1–8 |
| `RALLYMATE_SAM3D_BATCH_PERSONS` | `4` | 每次模型前向人物数上限，1–8 |
| `RALLYMATE_SAM3D_BATCH_GRAPH_SIZES` | 空 | 额外捕获的人物批尺寸，例如 `8`，最多两个 2–8 的不同值 |
| `RALLYMATE_SAM3D_FORWARD_GRAPH_BUDGET_MIB` | `512` | backbone 与六个 decoder layer 共享的额外批图保留预算，整数 128–4096 MiB |
| `RALLYMATE_SAM3D_HEAD_GRAPH_BUDGET_MIB` | `512` | body head 的额外批图合计保留预算，整数 128–4096 MiB |

图预算在新 worker 安装图优化时读取；已有进程和单人物图不随环境变量变化。非法值在安装前报错。回执记录实际预算及默认/环境来源；仍保留显存空闲门槛、超预算释放和 eager 回退。预算限制观测到的额外图保留增量，不是整卡显存上限，也不约束捕获瞬间峰值。2026-11-06 新增这两个受控参数，默认仍各 512 MiB，尚未据此提高生产预算或证明额外提速。后续可在空闲时用新隔离 worker 对照 forward 512/1024/2048 MiB，并保持 head 512 MiB及其它条件一致；比较图实际命中、峰值显存、完整结果与端到端耗时。

批图要求 BODY、body-head graph 和 rotation 优化开启。backbone/decoder layer 的批图还需要现有 `RALLYMATE_SAM3D_FORWARD_GRAPH=backbone_decoder_layers`。DINOv3 既有启动脚本会设置这些已验证的单帧基础优化；仅设置 `BATCH_FRAMES=8` 而保留 `BATCH_PERSONS=4` 会成为两次 4 人前向。

单人视频的 8 帧候选配置（**这是复测配置，不表示已部署**）：

```powershell
$env:RALLYMATE_SAM3D_BATCH_FRAMES = '8'
$env:RALLYMATE_SAM3D_BATCH_PERSONS = '8'
$env:RALLYMATE_SAM3D_BATCH_GRAPH_SIZES = '8'
```

环境变量必须在 worker 创建前传入；已有模型进程不会随 shell 环境变化。正式切换须使用现有空闲检查与重启流程。回退时设 `BATCH_FRAMES=1` 并清空 `BATCH_GRAPH_SIZES` 后重新启动 worker。

### 2026-11-07 三维交付与阶段调度复核

用户要求以完整三维交付和高性能任务吞吐为目标。1693.840秒仅计分析管线，不包含三维视频；此前同源三维渲染另有694.865秒记录，两段并非本轮同一次端到端测量。分段报告的响应速度不能代替这个指标。

已确认并修改的调度问题：

- 原 worker 只有分析队列为空才渲染三维，新 queued 任务还会终止当前渲染并从头重做。现在每次分析后给最早的一个合法三维任务完整执行机会，再认领下一分析；queued 不抢占，running 冲突/取消/停止/来源校验仍有效。20任务真实临时DB测试验证 analysis0、mesh0、analysis1、mesh1 的顺序。managed fleet 的 GL 路由仍未启用。
- SAM 请求期间主线程原来不准备下一批检测、跟踪、相机与身份状态。新增有界 FIFO 准备线程；只有检测/跟踪准备前移，SAM/secondary selector/发布仍由一个消费者顺序执行，且只支持隔离 SAM 进程。默认关闭，使用 `RALLYMATE_SAM3D_PIPELINE_OVERLAP=1` 启用。
- batch8 输出突发与仅2帧的归档队列不匹配，旧全片累计阻塞107.378秒。未显式设置归档上限时，现在按 SAM 帧批次选择2/4/8；显式上限继续有效，仍一个归档线程、按序校验后发布。
- 完整 decoder 图原来只接受 N=1/P=1，batch8 回退为分层图。新增默认空的 `RALLYMATE_SAM3D_DECODER_BATCH_GRAPH_SIZES=8`，共享原 forward 预算，保留6层/6个head/全部70点与18439顶点，不释放安全回退句柄。
- 三维 CPU 场景构造原来和 GL 串行。新增 `RALLYMATE_SAM3D_MESH_PREPARE_WORKERS=2` 候选，默认0；完整动态法线和 Trimesh process 保留，GL 始终在主线程，最多2个待消费任务加当前主线程帧。128MiB是提交场景的保守估算准入，不是RSS硬限制；超大帧回退同步处理。
