## 2. 建议采用的技术路线

保留 **React / Vinext + FastAPI + 独立 GPU Worker**。新增账户、审批和权限模块，生产主业务库采用 **PostgreSQL + SQLAlchemy + Alembic**，本地保留 SQLite 兼容运行方式。密码使用 **Argon2**，登录使用 **JWT + HttpOnly Cookie**。前端、业务 API 与账户 API 通过同源入口访问，减少 Cookie 和跨域配置的分歧。

这条路线复用现有 Python 服务与前端页面。SQLAlchemy 负责新增业务模型和 PostgreSQL 访问，Alembic 管理结构变更；现有 Worker 通过保持行为兼容的任务存储接口继续运行。密码哈希和令牌签验使用成熟库，接入依据见 [FastAPI 官方安全文档](https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/)。

三项边界贯穿实施：

1. **保护核心实现。** 视频校验、分片写入与合并、AI 姿态和球拍推理、评分、报告生成的内部实现保持原样。新增权限检查、归属登记和观测逻辑位于入口、存储适配或执行包装层。
2. **保护历史数据。** `jobs.user_id` 允许为空；旧记录保留原 ID、状态、摘要和文件。普通用户只查询 `user_id == 当前用户.id` 的记录，空归属不构成共享权限。
3. **保护既有运行语义。** 保留任务容量限制、原子领取、取消确认、执行尝试归属和故障恢复规则。数据库适配与队列回归共同验收。

## 3. 功能与修改清单

| 模块 | 建议改动 | 预期行为 |
|---|---|---|
| 用户模型 | 新增 `users`：UUID 主键、唯一邮箱、显示名称、`password_hash`、角色、状态、申请理由、创建时间、最近登录时间；角色为 `ADMIN/USER`，状态为 `PENDING/APPROVED/REJECTED/SUSPENDED` | 邮箱作为登录标识；注册默认 `USER + PENDING`，客户端不能提交管理员权限或审批结果 |
| 管理员初始化 | 从 `ADMIN_EMAIL`、`ADMIN_PASSWORD` 创建首个 `ADMIN + APPROVED` 账号；初始化支持并发和重复启动 | 已有管理员时不覆盖其密码，不重复创建；日志不输出密码 |
| 登录与会话 | 新增 `/api/auth/register`、`/api/auth/login`、`/api/auth/logout`、`/api/auth/me`；JWT 默认有效期 7 天，增加可撤销会话记录 | Cookie 使用 HttpOnly，生产启用 Secure、合适的 SameSite 和写操作 CSRF 防护；退出后原会话失效 |
| 输入与异常处理 | 邮箱规范化与格式校验、密码强度和长度限制、参数化查询、数据库唯一约束、注册登录限流、统一异常响应 | 重复与并发注册得到明确结果；错误响应不泄露数据库路径、堆栈或凭据 |
| 审批与鉴权 | 每次受保护请求读取当前用户及状态，统一校验登录、审批和权限 | 未登录返回 401；未通过审核返回带清晰原因的 403；管理员接口同时要求 `APPROVED + ADMIN` |
| 任务与上传归属 | 新增可空的 `jobs.user_id` 外键及查询索引，增加上传会话归属表；新用户任务在创建事务内绑定归属 | 创建、续传、合并和提交使用同一归属；普通用户不能读取或操作他人的任务与分片 |
| 登录和审核页面 | 新增登录、注册及审核状态页，注册支持申请理由；工作台、标注页增加入口守卫 | 公开介绍页可保留；审核通过后加载工作台，审核中、拒绝和封禁分别展示对应提示 |
| 个人历史 | 后端提供按用户过滤的分页历史；复用现有列表与回放入口，本地缓存按用户命名空间隔离 | 在不同设备登录可查看自己的服务端任务；切换账户不显示上一账户的历史、续传任务或结果 |
| 管理员后台 | 新增 `/admin` 及管理 API，支持状态筛选、通过、拒绝、封禁、删除用户、重置密码和操作审计 | 展示总用户数、待审核人数及各用户调用统计；普通用户无法通过直接请求管理 API 越权 |
| 删除与密码重置 | 用户删除建议采用逻辑删除，撤销所有会话并保留历史归属；重置使用一次性凭据流程；保护最后一个有效管理员 | 删除、封禁和重置后旧凭据不能继续访问；任务删除后从个人列表和资源访问入口移除 |

**统计口径：** 分别展示提交任务数与实际进入执行的尝试次数。自动重试计为新的执行尝试，排队后取消不计入执行次数，失败尝试仍计数；逻辑删除不抹去累计调用统计。无归属的历史记录不自动计入任何个人，迁移无法恢复的额外历史调用不补造数字。

**任务删除顺序：** 运行中的任务先走现有取消机制，等 Worker 确认终止后再执行删除和受控文件回收，避免删除仍在写入的产物。历史复核及管理审计保留原有追溯关系。

## 4. 权限接入与数据迁移边界

### 4.1 必须覆盖的访问路径

统一鉴权覆盖任务列表、创建、详情、进度、取消、删除，分块上传的创建、查询、写入和完成，以及原视频、三维回放、报告分页、下载、技术复核和击球统计。读取资源时先验证归属，再处理视频 Range、缓存和文件响应；上传请求在接收和解析大体积内容前检查权限。

现有代理会自动附加共享 API key，前端 `/api/advice` 也会用该 key 向后端读取任务。这两处必须传递并验证当前用户身份；共享服务密钥不能替代用户登录。开发代理、Node / Worker 网关和 Nginx 配置统一支持账户路由、Cookie、Set-Cookie 和 CSRF 校验。内部停机维护接口继续保留独立的运维权限。

现有浏览器历史、活动任务和上传续传键也需按用户隔离。旧公共键保留原内容，但不自动导入任意新账号；新用户的在线历史以服务器归属为准。

### 4.2 PostgreSQL 迁移范围

PostgreSQL 保存用户、会话、上传归属、主任务、管理审计及统计。视频和报告产物继续使用现有文件存储。上传会话内部的 `state.sqlite3`、现有技术复核及击球复核存储保留原实现，通过所属任务控制访问。

当前部分代码直接调用 `db.connect()`，Worker 依赖 `execution_reader()`。新存储适配必须兼容这些调用及原事务行为，并同步调整应用启动与监控入口。结构迁移由部署步骤串行执行，Worker 初始化负责幂等检查。

迁移流程为：**备份数据库与文件 → 停止旧库写入 → 创建新结构 → 导入任务并映射 Linux 路径 → 校验数量、ID、状态、摘要和文件引用 → 验证权限与回放 → 切换服务**。旧数据源保留用于恢复；切换后的新增数据纳入独立备份和回滚流程。空归属历史由受控管理员工具显式分配，不开放为全员共享记录。

## 7. 验收与交付标准

1. **账户闭环：** 注册后可登录查看审核状态；管理员审批通过后可使用工作台。重复注册、弱密码和无效输入得到正确响应，首管理员初始化可重复运行。
2. **权限矩阵：** 验证未登录、PENDING、APPROVED、REJECTED、SUSPENDED 和 ADMIN；退出、封禁、删除及密码重置后，旧会话的后续请求失效。
3. **双用户隔离：** 两个已审批用户交叉请求任务、分片、原视频、回放、报告、下载、问答和删除接口，均无法访问对方资源；列表和本地缓存不混用。
4. **迁移兼容：** 使用现有数据的备份演练，核对任务数量、ID、状态、摘要、产物引用和 Linux 路径映射；旧记录可保留且不泄露给普通用户。
5. **并发与业务回归：** 在真实 PostgreSQL 上验证并发注册、首管理员初始化、任务准入与原子领取；回归分片上传、续传、取消、视频 Range 和报告读取，保持既有核心行为。
6. **前端与部署：** 通过构建、类型检查和相应测试；在 Linux 目标环境完成启动、短视频全链路、CPU/GPU 指标采集、Sentry 错误上报及告警送达验证。

实施交付包括数据库迁移与导入脚本、`.env.example`、Compose 配置、监控仪表盘及告警规则、测试结果，以及可执行的本地测试、Linux 部署、备份恢复和回滚说明。测试证据分别记录本地环境与目标服务器的实际结果。

## 8. 方案评审入口

本方案建议一次交付账户审批、用户隔离、管理员后台、PostgreSQL 适配及监控配置；实施顺序为 **存储与迁移 → 后端权限 → 前端页面 → 部署监控 → 联合验收**。Uptime Kuma 默认作为可选服务，账号和历史隔离构成统一验收闭环。

用户可在阅读后选择调整范围、修改技术路线，或明确批准按本清单实施。本文交付本身不启动代码开发和数据库迁移。
